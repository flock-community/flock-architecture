# Specified contracts

Every system makes promises to whoever uses it. This deep dive is about writing those promises down: what a contract is, where it sits, and how it keeps you free to change everything behind it.

:::note

This deep dive is still being written. For now, the [overview](/) explains the idea in short.

:::

## What this deep dive will answer

- What is a contract, and where in a system do you need one?
- Why does it matter that the contract is specified, and not whether it was written before or after the code?
- How do versions and deprecation let you change things without surprising the people who rely on you?
- How do you know who is using what?
- What should you keep out of a contract, so you don't give away more than you can take back?

## Study material

- [The pragmatic repository](https://github.com/flock-community/pragmatic) keeps its contract as a specification, not as a by-product of the code. Look at the `api` module: the whole API is one short file in Wirespec, a small language for writing down what each endpoint accepts and returns, and the endpoints the application implements are generated from that file. The `spi` module does the same in the other direction: the client for a service the application calls is generated from that service's published specification.
