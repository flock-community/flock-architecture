# Event-driven

In an event-driven architecture, the parts of a system communicate by publishing **events**. An event is a record of a change of state in the business: a customer moved house, an order was placed. The part in which the change happens publishes it, and other parts react. Martin Fowler's article [What do you mean by "Event-Driven"?](https://martinfowler.com/articles/201701-event-driven.html) shows how much ground the term covers, from a simple notification to a system whose events are its source of truth.

What these forms share is a shift in focus. Most software describes the state: how things are now. An event-driven system describes the changes to that state.

## Storing state changes

Take the customer's address. In most systems it is a column in a table, updated when the customer moves, and the old address is gone. An event-driven system describes the move instead: this customer moved house, to this address, on this date. The current address follows from the latest move.

<StateHistoryFigure />

Storing state is enough for a great deal of software, but the questions a business asks are mostly about what happened. How many customers moved last quarter? A system that only stores state cannot answer that, because every update destroyed information. The idea is old. An accountant does not overwrite the balance, but adds an entry to the ledger, and the ledger is trusted because nothing in it is ever lost.

Event-driven does not mean that the events are kept. A system can react to every event, store the new state and discard the event. It then remains state-based at heart, but the step to [keeping the events](#keeping-the-events) is a small one.

## What makes a good event

An event is a fact, and every other property follows from that.

**It is named after what happened, in the past tense, in the words of the business.** Order placed. Payment received. Parcel handed to carrier, if that is the warehouse's own term. The names of the events form the vocabulary of the system. In an event storming workshop, the business and the engineers map a domain together. They write the events that matter within one [bounded context](/domain-isolation#bounded-contexts) on sticky notes. That wall of notes in the past tense is the first draft of the events.

**It carries what happened, not everything.** A move carries the customer's identifier, the new address and the date, not the whole customer record. Anything else it refers to [by identifier](/domain-isolation#contexts-do-not-overlap).

**It never changes.** A wrong fact is corrected by a new event, a **compensating event**, in the way an accountant reverses an entry instead of erasing it. Anything that can be edited afterwards is state, not history.

## Commands, queries and events

Many event-driven systems separate two responsibilities. A **command** asks for a change: place this order. A **query** asks for information: which orders did this customer place? **Command query responsibility segregation**, or CQRS, gives each of them a model of its own.

The **command model** decides whether a command is allowed and, if it is, records the change and publishes it as an event. The **query model** answers questions, in whatever shape suits them best, and keeps itself up to date by reacting to those events. Several query models can read the same events, including query models in other domains. A read-only copy that another domain keeps, as [Domain isolation](/domain-isolation#contexts-do-not-overlap) allows, is a query model of this kind.

The two models could share a database. We let them communicate through events, so the command model need not know who reads its changes.

A question that needs an immediate answer, such as whether a card is valid, is no reason to abandon events. It is a query, answered at once by a query model that events keep current.

### Eventual consistency

A query model reacts after the event, so there may be a delay before a change can be read. During that interval, the checkout domain knows about an order that the customer's order history does not yet show. This is **eventual consistency**: every model arrives at the same picture, but not at the same instant.

The business has always worked this way. The warehouse picks a parcel hours after the order is placed, and nobody regards that as an inconsistency. The question to ask at every boundary is how long a delay the business can accept.

## Keeping the events

So far, the events have been messages, discarded once every reader has handled them. The next step is to keep every event, permanently, in the order in which it happened.

That step changes what counts as the record. Once the events are kept, they hold the complete history, and every table can become a **projection**: a shape of the data made for one kind of question, which can be discarded and rebuilt from the events at any time. The order overview, the sales per day and the search index are each a different reading of the same events.

<ViewsFigure />

When the business asks for a report it never asked for before, a new projection reads the events from the beginning, and the report is complete on the day it is built, last year included. The history also serves as an audit trail, at no extra cost.

### Event streaming and event sourcing

In **event sourcing**, a domain uses its own events to decide what it may do next. To handle a command, it reads back the events of, for example, one order, derives the current state from them, decides whether the command is allowed and, if so, adds new events. The events are the source of truth, any state is derived from them, and nothing can change without an event that records it.

Everything else is **event streaming**: events are published and read, and perhaps kept, but the domain makes its decisions on stored state. Every event-sourced domain also streams its events, but a domain that streams events need not be event-sourced.

Event sourcing is not the goal of an event-driven system. It is one tool among several, and a choice per domain. It pays off where the history is the business itself: orders, payments, anything that may be disputed. For a table of countries, storing the state is enough. The choice is far easier in a system that is already event-driven. A system built on reading and writing tables would have to be redesigned first.

### Events that last

A stored event does not go away. An event written in the first year may seldom be read in the tenth, but it must remain readable, in whatever shape it had when it was written. An event that leaves its domain is a contract, and everything [Specified contracts](/specified-contracts) says about versions and compatibility applies to it.

## What it asks of a team

Event-driven is a way of thinking before it is a way of building. The question is no longer what to call to make something happen, but what happened. The publisher does not need to know who listens, and it does not matter whether anyone does.

The burden moves to the reader. A team that reacts to an event has to understand the context in which it was published, and that is often harder than understanding a request and its response. Names therefore deserve the care of a public interface from the first day, and the events of a system should be documented where every team can find them.

Personal data needs a decision before the first event with a name in it is written, because the right to be forgotten does not sit well with a record that cannot be edited. One answer is **crypto-shredding**: personal data in events is encrypted with a key per person, and forgetting that person means destroying the key.

No new infrastructure is needed to begin. A table of events in the database a team already has is a sound first event-driven system.

## Conclusion

An event is a fact: a change of state, named in the past tense and in the words of the business. An event-driven system with CQRS describes those changes instead of only the state they produce. Its command models publish what happened, and its query models build the views that questions need. That leaves a choice, per domain, of whether to keep the events and whether to make them, rather than the stored state, the source of truth. Whatever each domain chooses, the system remains an event-driven architecture with CQRS.

Events are what travels between the circles. [Domain isolation](/domain-isolation) is about what is inside a circle, [Specified contracts](/specified-contracts) about its edge, and the [overview](/) shows how the three depend on each other.
