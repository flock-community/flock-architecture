# Event-driven

A customer of the web shop from the [overview](/) moves house. Most software stores only state, so the move becomes an update to a field. An event-driven system describes state changes instead. The move is an **event**, a record of something that happened, and the system reacts to it.

Martin Fowler, in ["What do you mean by 'Event-Driven'?"](https://martinfowler.com/articles/201701-event-driven.html), observes that the term covers several patterns, from a simple notification to a system whose events are its only record. Event-driven, as we use it, means that a domain publishes what happened inside it and the rest of the system reacts. The publisher does not know who listens, which can make the system loosely coupled: one domain can change without the others changing with it.

Reacting to events does not require keeping them: a domain can receive an event, update its tables and discard it. The events are then ephemeral, gone once handled, and the system remains state-based at heart. Keeping them is an optional later step, easy in a system that already publishes them.

## Storing state changes

The customer's address is usually a column in a table, overwritten when the customer moves. In a system that keeps its events, the move itself is recorded and the old address is not lost. The current address follows from the latest move, and last year's address is still on record.

<StateHistoryFigure />

Storing state is enough for many systems, but the questions a business asks are mostly about what happened. A system that stores only state cannot say how many customers moved last quarter, because each update destroyed the information. The remedy is old. An accountant does not overwrite the balance but adds an entry to the ledger, which is trusted because nothing in it is ever lost.

## What makes a good event

An event is a fact, and everything else follows from that.

An event is named after what happened, in the past tense and in the words of the business. Order placed. Payment received. If the warehouse says that a parcel was handed to the carrier, the event is called "parcel handed to carrier", not "shipment dispatched", a name an engineer might invent.

Event names are the vocabulary of the system, and a good vocabulary lasts for years. In an event storming workshop, the business and the engineers write on sticky notes the events that matter for one [bounded context](/domain-isolation#bounded-contexts): the first draft of that vocabulary.

An event carries what happened, and no more. A move carries the customer's identifier, the new address and the date, not the whole customer record. It refers to everything else [by identifier](/domain-isolation#contexts-do-not-overlap).

An event is **immutable**: it never changes, because history cannot be edited. A move with the wrong date is not corrected in place. A **compensating event** undoes it and a new move records the right date, the way an accountant reverses an entry and posts a fresh one.

## Commands, queries and events

A **command** asks for a change and can be refused: move this customer to this address. A **query** asks for information and changes nothing: the current address of this customer. **Command query responsibility segregation**, or CQRS, gives each its own model. The **command model** applies the rules and decides whether a change is allowed. The **query model** holds the data in the shape that questions need.

We connect them with events: the command model accepts the move and publishes "customer moved house", and the query model updates the address it serves. The two models could share a database, but we choose events, because the same event also serves every other listener.

Shipping, the domain that delivers the parcel, holds a [read-only copy](/domain-isolation#contexts-do-not-overlap) of the delivery address: a query model of its own, kept current by the same event. Whether an item is in stock is a query too, put to the query model of the domain that owns the stock.

### Eventual consistency

The query model updates after the event, so for a short time the command model knows of a move the query model has not yet seen. This is **eventual consistency**: the new state reaches every reader, but only after a delay.

Shipping's copy of the address is updated a moment after the customer confirms the move, and a moment is of no consequence to a parcel that leaves tomorrow.

## Keeping the events

A domain may also keep every event, permanently and in order, instead of discarding it once handled.

Every table built from the events becomes a **projection**: a query model shaped for one kind of question. The order overview, the sales per day and the search index are different readings of the same events. The events, once ephemeral, are now the record of what happened, and any projection can be discarded and rebuilt from them.

<ViewsFigure />

When the business asks for a report nobody foresaw, a new projection reads every event from the first, and the report is complete on the day it is built, last year included. An audit trail, the record of what changed and when, needs no extra work: the events are that record.

An event that leaves a domain is a contract. The versioning rules in [Specified contracts](/specified-contracts) apply, with one difference: a published event cannot be switched off. An event from the first year is rarely read in the tenth, but it must remain readable, and a reader has to cope with every shape ever published.

### Event streaming and event sourcing

Keeping the events is not yet event sourcing. In **event streaming**, a domain publishes its events for others to read, whether or not anyone keeps them, and takes its decisions from state it stores in a table.

In **event sourcing**, a domain takes its decisions from its own events. To handle a move, it reads the customer's events, derives the current state, decides whether the move is allowed and, if so, appends new events. The events are the only thing the command model writes, and so become the **source of truth**, from which everything else is derived. An event-sourced domain publishes the events others need, so event sourcing implies event streaming, never the reverse.

Event sourcing is not the destination but one tool among several, chosen per domain. It fits orders and payments, where the history is the business, and is excessive for a list of countries, where a table of state is enough. Where every change is already recorded as an event, the step is within reach. In a system that stores only state, event sourcing is far harder to add and usually means a redesign.

## What it asks of a team

Event-driven is a way of thinking before it is a way of building. The question is no longer which system to call to make something happen, but what has happened. A domain publishes its events without regard to who needs to know, and if nobody listens, no harm is done.

The effort moves from publisher to listener, who has to know the circumstances in which an event was published. Building a projection requires understanding much of the system, which is often harder than understanding an interface and its data. The name of an event therefore deserves the care of a public interface, because renaming a published event is a migration: every listener has to change with it. A system's events also have to be documented or discoverable.

Personal data poses a problem, because an immutable event cannot be deleted. The usual answer is **crypto-shredding**. The personal fields in an event, such as the address in a move, are encrypted with a key per customer. When the customer exercises the right to be forgotten, the key is destroyed. The event remains unchanged, but its personal fields can no longer be read.

Starting with events requires no new infrastructure. A table of events in the database the team already has is a sound place to begin.

## Conclusion

An event-driven system describes state changes instead of state, and reacts to them. Each event is a fact, named in the past tense and in the words of the business. With CQRS, one model decides on commands, another answers queries, and events carry the changes between them. Such a system gives each domain the option to store what happened instead of the state that followed, and whichever way each domain decides, the architecture remains the same: event-driven, with CQRS.

Events are what travels between the circles. [Domain isolation](/domain-isolation) is about what is inside a circle, [Specified contracts](/specified-contracts) about its edge, and the [overview](/) shows how the three depend on each other.
