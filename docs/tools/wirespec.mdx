# Wirespec

[Wirespec](https://wirespec.io) is a small language for writing down the contract of an interface, and a compiler that turns that contract into code. It is open source, built and maintained by Flock, and it belongs with the [Specified contracts](/specified-contracts) pillar. It is the tool we use to put that idea into practice.

## What it is

A Wirespec file describes an interface in a handful of building blocks: the **types** that travel over the wire, the **endpoints** that accept them and what each endpoint answers, and **channels** for messages that are sent rather than requested. There is little more to the language than that. A file with a few of each is a complete contract.

```wirespec title="todos.ws"
type Todo {
    id: Integer,
    task: String,
    done: Boolean
}

endpoint GetTodos GET /todos -> {
    200 -> Todo[]
}

endpoint CreateTodo POST Todo /todos -> {
    201 -> Todo
    400 -> Error
}

type Error {
    reason: String
}
```

This file says that a to-do has an identifier, a task and a done flag; that a list of them can be fetched from `/todos`; and that a new one can be sent to the same address, which answers either with the created to-do or with an error. Anyone can read it, including people who never write code, and it names everything the two sides need to agree on.

From such a file the Wirespec compiler generates code in the language of each party: Kotlin, Java, TypeScript and Python, among others. The generated code holds the types and, for each endpoint, its request and every response it can give, in a form that the compiler of that language checks. It depends on no library or framework, so it fits into any project and outlives the frameworks around it. Wirespec plugs into the usual build tools, Maven, Gradle and npm, and into IntelliJ IDEA and Visual Studio Code. There is also an online [playground](https://playground.wirespec.io) to try it in.

## Where it fits: Specified contracts

[Specified contracts](/specified-contracts) is about making the promises a system makes to the outside world explicit: written down, versioned and shared, so everyone knows what is safe to change. A Wirespec file is that explicit promise. It is the contract itself, in a form that both people and compilers can read.

Two things follow from generating the code instead of writing it by hand:

- **The contract can't drift from the code.** The code that speaks the interface is generated from the specification, so it can't quietly diverge from it. When the contract changes, the generated code changes with it, and everything built on that code either still compiles or shows exactly where it broke.
- **Both sides work from the same file.** The team that provides an interface and the teams that consume it generate their code from one specification. A change to the contract is visible to every consumer at once, before anything is deployed.

Wirespec's own documentation calls this *contract-first*: writing the specification before the code. That order is the natural one for a new interface, but it isn't what the pillar hinges on. What matters is that a specification exists and is the source of truth, and Wirespec serves an existing interface just as well.

## Wirespec and OpenAPI

OpenAPI is the most widely used standard for describing web APIs, and it works fine. You don't need Wirespec to have a specified contract. So why did we build it?

Because a contract is read far more often than it is written. Here is the to-do contract from above, written in OpenAPI.

<details>
<summary>The same contract in OpenAPI</summary>

```yaml title="todos.yaml"
openapi: 3.0.3
info:
  title: Todos
  version: 1.0.0
paths:
  /todos:
    get:
      operationId: GetTodos
      responses:
        "200":
          description: The to-dos
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/Todo"
    post:
      operationId: CreateTodo
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/Todo"
      responses:
        "201":
          description: The created to-do
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Todo"
        "400":
          description: Why the to-do was refused
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Error"
components:
  schemas:
    Todo:
      type: object
      required: [id, task, done]
      properties:
        id:
          type: integer
        task:
          type: string
        done:
          type: boolean
    Error:
      type: object
      required: [reason]
      properties:
        reason:
          type: string
```

</details>

It says the same thing in about three times as many lines, and most of those lines are structure, not content. That matters most when the contract changes, because every change goes through a review. A new field in Wirespec is one line in a pull request, and the reviewer sees at once what changes for consumers. In OpenAPI the same field takes a few lines, deep in the YAML, plus an entry in a separate list of required fields.

You don't have to choose between the two. Wirespec converts an OpenAPI description into a Wirespec file, so an interface that grew without a contract gets one after the fact. And it produces OpenAPI from a Wirespec file for the tools that expect that format.

## What it brings

- **Contract changes that are easy to review.** A change to the contract shows up in a pull request as a few readable lines, so reviewers see what changes for consumers.

- **A contract that non-programmers can read.** A product owner or a manager can read a Wirespec file and check that it says what was agreed.
- **One source of truth for an interface**, independent of any language, with generated code that is guaranteed to match it.
- **Less repetitive work.** The types and the plumbing for every request and response are generated, so engineers write only the behaviour behind the interface.
- **Early warning when a change breaks someone.** Consumers find out when they compile, not when they deploy.
- **A basis for testing.** The specification can drive mock servers and test data, so an implementation can be checked against the contract it claims to follow.
